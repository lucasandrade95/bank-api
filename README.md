# Bank API

REST API de operações bancárias (contas e transações) construída em **Java 21 + Spring Boot 3**.
Projeto de portfólio com foco em backend bancário: regras de negócio financeiras, testes automatizados, documentação OpenAPI e containerização.

> Em construção — evoluído com commits diários. Acompanhe o [roadmap](#roadmap).

## Stack

- Java 21, Spring Boot 3.3
- Spring Web, Spring Data JPA, Bean Validation
- H2 (dev/teste) e PostgreSQL (profile `postgres`), com schema versionado por Flyway
- springdoc-openapi (Swagger UI)
- JUnit 5, MockMvc
- Docker (multi-stage), GitHub Actions (CI)

## Como rodar

```bash
# testes
mvn clean verify

# subir a aplicação (porta 8080)
mvn spring-boot:run

# ou via Docker
docker build -t bank-api .
docker run -p 8080:8080 bank-api
```

Por padrão a aplicação sobe com **H2 em memória** (schema criado pelo Hibernate),
ideal para rodar e testar sem dependências externas.

Para usar **PostgreSQL** com migrações **Flyway** (mais próximo de produção):

```bash
# sobe um Postgres local
docker compose up -d

# roda a API no profile postgres (Flyway aplica db/migration/*.sql no boot)
mvn spring-boot:run -Dspring-boot.run.profiles=postgres
```

- Swagger UI: http://localhost:8080/swagger-ui.html
- H2 console (apenas no profile padrão): http://localhost:8080/h2-console (JDBC `jdbc:h2:mem:bankdb`, user `sa`)

## Endpoints (v1)

| Método | Rota                       | Descrição                |
|--------|----------------------------|--------------------------|
| POST   | `/api/v1/auth/register`         | Cadastra usuário e devolve JWT |
| POST   | `/api/v1/auth/login`            | Autentica e devolve JWT       |
| GET    | `/api/v1/users/me`              | Perfil do usuário autenticado: `id`, `username`, `createdAt` (nunca senha/hash) 🔒|
| PUT    | `/api/v1/users/me/password`     | Troca a senha do usuário autenticado (exige a senha atual) 🔒|
| POST   | `/api/v1/accounts`              | Cria conta (saldo zero) 🔒    |
| GET    | `/api/v1/accounts`              | Lista contas paginadas e filtráveis por situação (`?page=&size=&status=`) 🔒|
| GET    | `/api/v1/accounts/{id}`         | Consulta conta por id         |
| POST   | `/api/v1/accounts/{id}/deposit` | Deposita valor na conta       |
| POST   | `/api/v1/accounts/{id}/withdraw`| Saca valor (valida saldo)     |
| POST   | `/api/v1/accounts/{id}/transfer`| Transfere para outra conta (atômico) |
| POST   | `/api/v1/accounts/{id}/block`   | Congela a conta (bloqueia movimentação) 🔒|
| POST   | `/api/v1/accounts/{id}/unblock` | Reativa a conta 🔒|
| POST   | `/api/v1/accounts/{id}/close`   | Encerra a conta (exige saldo zero) 🔒|
| GET    | `/api/v1/accounts/{id}/statement`| Extrato da conta paginado e filtrável por período e tipo (`?page=&size=&from=&to=&type=`) 🔒|
| GET    | `/api/v1/accounts/{id}/statement/summary`| Resumo do extrato: totais de entrada/saída e detalhe por tipo no período (`?from=&to=`) 🔒|
| GET    | `/api/v1/accounts/{id}/statement/{transactionId}`| Comprovante de um único lançamento do extrato 🔒|
| GET    | `/api/v1/accounts/{id}/limits`  | Limites da conta: teto diário de débito, usado e disponível hoje 🔒|
| GET    | `/api/v1/accounts/health`       | Health check                  |
| GET    | `/actuator/health`              | Health do app (probes)        |
| GET    | `/actuator/info`                | Metadados do app              |
| GET    | `/actuator/metrics`             | Métricas (JVM, HTTP, negócio) 🔒|

> 🔒 = exige `Authorization: Bearer <token>`. As rotas de conta são protegidas; obtenha um token em `/api/v1/auth/register` ou `/api/v1/auth/login`.

> As saídas de dinheiro (`withdraw` e `transfer`) respeitam um **limite diário de débito** por conta — o total que pode sair dela num mesmo dia UTC. Estourar o limite volta **422** informando quanto ainda há disponível hoje. Depósito e transferência recebida não consomem o limite. O teto é configurável (`bank.limits.daily-debit`, padrão `10000.00`). Para saber quanto ainda cabe **antes** de tentar a operação, consulte `GET /accounts/{id}/limits`.

> O **CPF do titular volta mascarado** em toda resposta (`***.456.789-**`) — ele entra inteiro na criação da conta e é guardado inteiro, mas não sai inteiro. O identificador da conta continua sendo o `id` (UUID), então nada no contrato depende do documento completo.

> As operações de dinheiro aceitam uma **`description` opcional** (até 140 caracteres) — "aluguel", "pix do almoço" — que fica gravada no lançamento e volta no extrato e no comprovante. Numa transferência as **duas pernas** recebem a mesma descrição. Espaços nas pontas são removidos e um texto em branco vale como ausente (`null`).

> As operações de dinheiro (`deposit`, `withdraw`, `transfer`) e a **criação de conta** aceitam um cabeçalho opcional `Idempotency-Key`: reenviar a mesma requisição com a mesma chave devolve a resposta original sem repetir a operação (útil para *retry* seguro após timeout — na criação, o reenvio devolve **201 com a mesma conta** em vez do 422 de "já existe conta para o documento"). Use **uma chave por operação**: a chave fica ligada à requisição que a gerou, então reusá-la em outra operação, conta, valor ou descrição volta **409**. A chave é **sua**: ela vive no escopo do cliente autenticado, então dois clientes podem escolher a mesma string sem interferir um no outro. A chave vale por **24h** (`bank.idempotency.retention`) — depois disso ela é expurgada e um *retry* tardio executa a operação de novo.

Exemplo (registrar, pegar o token e criar conta autenticado):

```bash
# 1) cadastrar e capturar o token
TOKEN=$(curl -s -X POST http://localhost:8080/api/v1/auth/register \
  -H "Content-Type: application/json" \
  -d '{"username":"lucas","password":"supersecret1"}' | jq -r .token)

# 2) usar o token nas operações de conta
curl -X POST http://localhost:8080/api/v1/accounts \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"ownerName":"Lucas Andrade","document":"12345678901"}'
```

## Decisões de design

- **Saldo em `BigDecimal`** (nunca `double`) — evita erro de arredondamento em dinheiro.
- **Escala monetária normalizada em 2 casas (`Money.normalize`)** — todo valor que a API devolve (saldo, valor de lançamento no extrato, valor de transferência, totais do resumo do extrato) passa por um único utilitário `Money.normalize` que fixa a escala em 2 casas decimais (centavos), a mesma das colunas `precision = 19, scale = 2`. Sem isso, o `BigDecimal` preservaria a escala crua do input: um depósito de `10.5` voltaria `"10.5"` e dois `10.5` virariam `"21.0"` — o mesmo valor exibido com escalas diferentes em respostas diferentes. Como a entrada já é validada para no máximo 2 casas (`@Digits(fraction = 2)`), a normalização na prática só completa zeros à direita; o `RoundingMode.HALF_EVEN` (arredondamento bancário) é salvaguarda, não caminho ativo. A regra mora no domínio (`Account.deposit/withdraw` normalizam o saldo, o construtor de `Transaction` normaliza o lançamento) — não numa formatação de apresentação que alguém poderia esquecer de aplicar.
- **DTOs (records) separados da entidade** — entidade JPA não vaza pela API.
- **Tratamento de erro centralizado** (`@RestControllerAdvice`) com corpo de erro padronizado.
- **Arquitetura em camadas** controller → service → repository.
- **Autenticação JWT stateless** (Spring Security) — senha guardada como hash BCrypt, segredo do token via configuração/env, filtro `OncePerRequestFilter` valida o `Bearer` em cada requisição.
- **Schema versionado por Flyway** no profile `postgres` (`ddl-auto: validate`) — em produção o banco é dono do schema e o Hibernate apenas valida que as entidades batem; H2 com `ddl-auto: update` segue para dev/teste rápidos.
- **Extrato paginado e filtrável por período** — o extrato nunca devolve todos os lançamentos de uma vez (uma conta pode ter milhares); o cliente pede `page`/`size` e recebe um envelope `PageResponse` (`content` + `totalElements`/`totalPages`/`last`). O `size` é limitado (1–100) para proteger banco e payload, e a ordenação fica fixa no servidor (mais recente primeiro) — o cliente não escolhe a ordem. As datas opcionais `from`/`to` (formato ISO `YYYY-MM-DD`, ambas inclusivas) restringem o extrato a uma janela — ex.: "extrato de janeiro" com `from=2026-01-01&to=2026-01-31`. Internamente vira um intervalo semi-aberto em UTC (`[from 00:00, (to+1 dia) 00:00)`) para o dia final entrar por completo; a filtragem é feita no banco (não em memória), então continua barata mesmo em contas grandes. Um período invertido (`from` depois de `to`) volta **400** no mesmo corpo de erro padrão. Um filtro opcional `type` (`DEPOSIT`/`WITHDRAWAL`/`TRANSFER_IN`/`TRANSFER_OUT`, combinável com o período) restringe o extrato a um único tipo de lançamento — ex.: "só os saques" com `type=WITHDRAWAL`; a filtragem também é feita no banco (mesma query, parâmetro anulável) e um valor de tipo inexistente volta **400** pelo handler de tipo já existente.
- **Resumo do extrato (totais do período)** — além do extrato lançamento a lançamento, `GET /accounts/{id}/statement/summary` devolve os **totais consolidados** de um período: `totalIn` (créditos: depósitos e transferências recebidas), `totalOut` (débitos: saques e transferências enviadas), `net` (saldo líquido = entrou − saiu) e um `byType` com contagem e soma de cada tipo de lançamento presente. Serve para o cliente montar um painel ("quanto entrou e saiu no mês?") sem baixar o extrato inteiro e somar do lado dele. A soma é feita **no banco** com uma única agregação `group by` (`TransactionRepository.summarizeByType`), então continua barata numa conta com milhares de lançamentos — nada é carregado em memória para totalizar. Reusa o mesmo período opcional `from`/`to` do extrato (datas ISO inclusivas, intervalo semi-aberto em UTC) e o mesmo **400** para período invertido; a classificação entrada/saída mora no domínio (`TransactionType.isCredit()`), não no service.
- **Comprovante de um lançamento (`GET /accounts/{id}/statement/{transactionId}`)** — além do extrato paginado, o cliente pode buscar **um único lançamento** pelo id (o "comprovante" de uma operação, ex.: para abrir num detalhe ou anexar num chamado). Reusa o mesmo `TransactionResponse` do extrato — sem contrato novo. O ponto de design é a **segurança**: a busca é **escopada à conta** do path (`TransactionRepository.findByIdAndAccountId`), então um id de lançamento válido mas de **outra conta** volta **404**, nunca o comprovante alheio — um IDOR clássico (referência direta insegura a objeto) evitado no repositório, não só no controller. Conta inexistente também volta **404**.
- **Observabilidade com Actuator + Micrometer** — `/actuator/health` e `/actuator/info` ficam públicos (úteis para probes de orquestrador/load balancer); `/actuator/metrics` exige token. Além das métricas técnicas (JVM, HTTP), há uma métrica de negócio `bank.account.operations` (counter com tag `type` = `deposit`/`withdrawal`/`transfer`) que conta operações concluídas — ou seja, **committadas** (ver o item sobre contagem depois do commit).
- **Request id (correlation id)** — um filtro (`RequestIdFilter`, primeiro da cadeia) atribui a cada requisição um identificador: usa o cabeçalho `X-Request-Id` enviado pelo cliente/gateway ou gera um UUID quando ausente. O valor entra no `MDC` do SLF4J (aparece em todas as linhas de log da chamada, via `logging.pattern.level`) e volta no cabeçalho `X-Request-Id` da resposta — assim dá pra correlacionar logs espalhados de uma mesma chamada e o cliente tem uma referência ao abrir um chamado de suporte. O MDC é limpo ao final de cada requisição para não vazar o id para a próxima que reutilize a thread.

- **Request id do cliente é validado antes de entrar no log** — o `X-Request-Id` é o único valor **controlado pelo cliente** que a API reimprime em **toda linha de log** da requisição, então aceitá-lo cru dá ao cliente uma caneta para escrever no log de quem opera a API. São dois abusos: **volume** — um id de vários KB (até o teto de cabeçalho do container) multiplicado por cada linha de log da chamada é um jeito barato de inflar o custo de observabilidade de fora para dentro; e **log forging** — um valor com separadores imita o formato das nossas linhas e planta uma linha falsa, corrompendo justamente a trilha que o request id existe para tornar confiável. O filtro só aceita o id do cliente se ele parecer um id de correlação: até **64 caracteres** de `[A-Za-z0-9._:-]`, o que cobre os formatos usuais (UUID, ULID, o hex do `traceparent` do W3C, ids com prefixo de serviço) sem deixar passar espaço, controle ou pontuação que atrapalhe a leitura de um log. O ponto de design é o que acontece com um id fora do formato: **não** é um 400. O request id é diagnóstico, não parte do contrato de negócio — recusar uma transferência válida por causa de um cabeçalho de observabilidade mal formado trocaria um problema pequeno por um grande. A degradação é silenciosa e segura: a API gera o próprio id, a chamada segue normal e o cliente vê na resposta que o id devolvido não é o que ele mandou. Vale como **defesa em profundidade**: quebra de linha em cabeçalho já é barrada antes (o `StrictHttpFirewall` do Spring Security recusa caracteres de controle, e o container trata CR/LF como fim de cabeçalho) — por isso esse caso é testado direto no filtro, sem passar pela cadeia; o que a proteção de fora deixa passar (espaço, `<`, `>`, tamanho) para no filtro.
- **Validação de CPF com dígitos verificadores** — o `document` da conta não é só `\d{11}`: uma constraint customizada (`@Cpf`, com `CpfValidator`) confere os dois dígitos verificadores pelo algoritmo módulo 11 e rejeita números matematicamente impossíveis (ex.: `12345678901`) ou de dígitos repetidos (ex.: `00000000000`) — exatamente o que um banco real recusaria. Como é uma anotação Bean Validation, a checagem roda na borda (DTO) e a falha cai no mesmo corpo de erro padrão (`400`). A entidade JPA não revalida: a validação de entrada é responsabilidade da camada de API.
- **Encerramento de conta (close)** — o titular pode encerrar a conta definitivamente via `POST /accounts/{id}/close`, transicionando o `status` para `CLOSED`. É o estado **terminal** do ciclo de vida da conta (`ACTIVE`/`BLOCKED`/`CLOSED`): uma conta encerrada rejeita **qualquer** movimentação (depósito, saque e transferência, pelas mesmas `Account.ensureActive()`) e não volta mais a outro status — `block`/`unblock` sobre ela falham (a checagem `ensureNotClosed()` impede que um `unblock` reabra uma conta encerrada). O encerramento só é permitido com **saldo zero** — como um banco real, o cliente precisa sacar ou transferir todo o saldo antes; tentar encerrar com saldo volta **422** no corpo de erro padrão. A operação é **idempotente**: encerrar uma conta já encerrada devolve **200** sem efeito. A regra mora no domínio (`Account.close()`), reusando o `status` já existente — **sem nova migração** (a coluna `status` é `VARCHAR(20)` e comporta o novo valor).
- **Congelamento de conta (freeze)** — a conta tem um `status` (`ACTIVE`/`BLOCKED`) e endpoints `POST /accounts/{id}/block` e `/unblock`. Uma conta `BLOCKED` rejeita **qualquer** movimentação — depósito, saque e as duas pernas de uma transferência (origem *e* destino) —, refletindo o que um banco faz ao congelar uma conta por suspeita de fraude, ordem judicial ou pedido do titular. A regra mora no domínio (`Account.ensureActive()`, chamada por `deposit`/`withdraw`), então nenhuma operação escapa dela e uma transferência para um destino bloqueado falha **atomicamente** (rollback, ninguém é debitado). A operação barrada volta **422** no corpo de erro padrão; `block`/`unblock` são idempotentes. Migração Flyway `V3__add_account_status.sql` para o profile `postgres`.
- **Travamento otimista no saldo (`@Version`)** — a conta tem uma coluna `version` que o JPA inclui em cada `UPDATE` (`... WHERE version = ?`) e incrementa. Se duas operações concorrentes leem o mesmo saldo e tentam gravá-lo, a segunda atualiza zero linhas e falha — evita o *lost update* (uma operação sobrescrever silenciosamente o saldo da outra). A perdedora recebe **409 Conflict** (mesmo corpo de erro padrão) e pode simplesmente repetir a requisição com o saldo já atualizado. Sem bloqueio pessimista no banco: mais escalável para o caso comum de baixa contenção.
- **Listagem de contas paginada e filtrável por situação** — `GET /api/v1/accounts` devolve as contas no mesmo envelope `PageResponse` do extrato (`content` + `totalElements`/`totalPages`/`last`), nunca um array cru: o número de contas cresce sem limite, então a listagem sempre vem em páginas (`page`/`size`, com `size` limitado a 1–100 pelas mesmas anotações `@Min`/`@Max` do extrato — um pedido abusivo volta **400**). A ordenação (mais recente primeiro) fica **fixa no servidor** (dentro da própria query do repositório, `AccountRepository.findByStatus`), não no `Pageable` — o cliente controla só paginação e filtro, nunca a ordem, seguindo a mesma decisão do extrato. Um filtro opcional `status` (`ACTIVE`/`BLOCKED`/`CLOSED`) restringe a listagem a uma única situação de conta — ex.: "só as contas ativas" com `status=ACTIVE`, para um painel esconder contas bloqueadas ou encerradas. A filtragem é feita **no banco** (mesma query, parâmetro anulável — mesmo padrão do filtro `type` do extrato), então continua barata mesmo com muitas contas; quando o `status` é omitido a listagem traz contas de qualquer situação, e um valor inexistente volta **400** pelo handler de tipo já existente. Reusa o `PageResponse` e o padrão de validação já existentes, sem inventar formato novo.
- **Idempotência das operações com dinheiro (`Idempotency-Key`)** — depósito, saque e transferência aceitam um cabeçalho opcional `Idempotency-Key`. Quando o cliente sofre um timeout e não sabe se a requisição chegou, ele reenvia com a mesma chave: na primeira vez a operação executa e a resposta é guardada (tabela `idempotency_keys`, a chave é `PRIMARY KEY`); numa repetição a API devolve a **resposta original** sem reexecutar o efeito colateral — nada de depósito ou transferência em duplicidade. O registro da chave é gravado **dentro da mesma transação** da operação, então se ela falha (ex.: saldo insuficiente) o rollback também desfaz a chave: só operações concluídas com sucesso ficam memoizadas e uma tentativa que realmente falhou pode ser refeita com a mesma chave. Sem cabeçalho, o comportamento é o de antes (idempotência é opt-in, retrocompatível). Duas requisições concorrentes com a mesma chave colidem na `PRIMARY KEY` e a segunda volta **409**. Migração Flyway `V4__add_idempotency_keys.sql` para o profile `postgres`.
- **Chave de idempotência ligada à requisição que a gerou (*fingerprint*)** — guardar só a resposta sob a chave não basta: a chave precisa saber **a que requisição ela responde**. Junto da resposta vai uma impressão digital do pedido (SHA-256 de `operação + conta + valor`, coluna `request_fingerprint`). Numa repetição a API compara: bateu, é um *retry* legítimo e devolve a resposta guardada; não bateu, a chave está sendo **reusada** em outro pedido e volta **409**. Sem esse vínculo a chave era global e o modo de falha era silencioso e caro: um cliente que reaproveitasse a chave por engano (uma por sessão em vez de uma por operação) mandaria um saque e receberia **200 com a resposta do depósito anterior** — o saque nunca aconteceria e nada indicaria o erro; entre operações de tipos diferentes, a resposta guardada sequer encaixa no contrato de saída. O 409 é a escolha conservadora: reexecutar quebraria a promessa da chave e devolver a resposta guardada seria mentir, então a API recusa e o cliente corrige a chave. A comparação é de **dinheiro, não de texto** (o valor passa pelo mesmo `Money.normalize`), então um *retry* que manda `10.5` onde antes mandou `10.50` continua sendo o mesmo pedido. Guarda-se o **hash**, não o pedido cru — a comparação só precisa responder "é a mesma requisição?", nunca reconstruir o original, e uma tabela de controle não vira cópia dos dados da operação. Migração Flyway `V5__add_idempotency_request_fingerprint.sql`.

- **`Idempotency-Key` validada na borda (tamanho ligado à coluna)** — a chave de idempotência é persistida numa coluna de tamanho fixo (`VARCHAR(255)`), então uma chave grande demais **estouraria a coluna** — só que no `flush`, lá dentro do service, virando uma `DataIntegrityViolationException`. Essa exceção cai na rede de segurança genérica do handler, que **não sabe qual restrição falhou** e responde **409 "conflito de concorrência"** — uma causa errada que manda o cliente investigar uma corrida que nunca houve (o mesmo modo de falha enganoso que o item do CPF acima corrige, aqui evitado na entrada). A checagem agora mora na **borda**: um `@Size(max = 255)` no cabeçalho recusa a chave com **400** no corpo de erro padrão, antes de qualquer efeito colateral. O limite não é um número solto — é a constante `IdempotencyRecord.KEY_MAX_LENGTH`, usada **tanto** no `@Column(length = ...)` **quanto** na validação, então coluna e contrato ficam provavelmente em sincronia: uma chave que passa na validação sempre cabe na coluna. Chave ausente ou em branco continua desligando a idempotência (o `@Size` aceita `null`/vazio), mantendo o comportamento opt-in.

- **Unicidade do CPF garantida pelo banco, não pela checagem (*check-then-act*)** — a criação de conta consulta `existsByDocument` antes de inserir, mas essa checagem **não fecha a corrida**: entre o "já existe?" e o `INSERT` há uma janela em que outra requisição com o mesmo CPF pode inserir primeiro, e as duas passam pela checagem. Quem garante a unicidade de fato é a restrição **UNIQUE** da coluna `document` — a checagem é só um atalho para dar uma mensagem boa no caso comum. O ponto é o que acontece com quem **perde** a corrida: a violação da restrição vinha subindo até o handler genérico de `DataIntegrityViolationException` e virava **409 "Idempotency-Key duplicada"** — uma resposta que aponta uma causa errada e manda o cliente investigar uma chave que ele nem enviou. Agora o service traduz a violação para a **mesma** `BusinessException` do caminho feliz: o cliente recebe **422** com a mesma mensagem, tenha perdido a corrida ou não — o comportamento da API não depende de timing. O `saveAndFlush` é o detalhe que faz funcionar: sem o *flush* explícito o `INSERT` só sairia no commit da transação, **fora** do alcance do `catch`. O handler genérico continua existindo como rede de segurança, mas com mensagem genérica de propósito — ele não sabe qual restrição falhou, então quem conhece a causa traduz antes de chegar lá.

- **Unicidade do username tratada como a do CPF (mesma corrida, mesma resposta)** — o cadastro de usuário tinha exatamente o *check-then-act* do item acima: `existsByUsername` antes do `INSERT`, com a mesma janela em que dois cadastros concorrentes passam os dois pela checagem. Quem garante a unicidade é a restrição **UNIQUE** de `users.username`; a checagem é só o atalho para a mensagem boa no caso comum. O problema era o que o perdedor recebia: a violação subia até o handler genérico de `DataIntegrityViolationException` e virava **409 "conflito de concorrência na gravação, requisição já em processamento"** — uma resposta que **convida ao retry**, e o retry de um username já tomado nunca vai dar certo. O cliente ficava repetindo uma tentativa condenada em vez de simplesmente escolher outro nome. Agora o service traduz a violação para a **mesma** `BusinessException` do caminho feliz: **422 "Username ja esta em uso"**, tenha o cadastro perdido a corrida ou não — o comportamento da API não depende de timing. O `saveAndFlush` é o mesmo detalhe do CPF: sem o *flush* explícito o `INSERT` só sairia no commit da transação, fora do alcance do `catch`. A lição transversal: quando duas rotas dependem da mesma restrição do banco, corrigir uma e esquecer a outra deixa o comportamento da API **inconsistente entre endpoints** — o handler genérico continua sendo rede de segurança, nunca o tratador de um caso conhecido.

- **Falha inesperada é 500 genérico, nunca 400 nem detalhe interno vazado** — o handler global traduzia `IllegalArgumentException` inteira para **400**. Só que `IllegalArgumentException` é a exceção mais genérica do Java: ela sobe do JDK, de qualquer biblioteca ou de um bug nosso. O efeito era uma API que respondia **"sua requisição está malformada"** para uma falha que podia ser um defeito do servidor — e ainda devolvia a **mensagem interna** da exceção no corpo (nome de tabela, coluna, trecho de SQL), tanto uma pista para quem sonda a API quanto um diagnóstico errado para o cliente, que fica corrigindo uma requisição que estava certa. É o mesmo modo de falha dos itens acima (a rede genérica respondendo por uma causa que ela não conhece), aqui na camada mais externa. Agora o 400 vem de um tipo próprio, `InvalidRequestException`, lançado **de propósito** para erro de entrada — hoje só o período invertido do extrato; o resto cai numa rede de segurança que devolve **500** com mensagem **fixa e genérica**, e o detalhe real vai para o **log do servidor** com stack trace. Como o `RequestIdFilter` põe o id da requisição no MDC, a linha de log sai correlacionada com o `X-Request-Id` que o cliente recebeu: o suporte acha a falha exata a partir do id que ele reportar, sem a API ter contado nada a mais. A rede de segurança **preserva o status** dos erros que o próprio Spring MVC levanta (rota inexistente **404**, método não suportado **405**, Content-Type inválido **415**): essas exceções implementam `ErrorResponse` e já trazem o status certo, então só o corpo é reescrito para o `ApiError` padrão — tratá-las como 500 transformaria um erro de rota do cliente numa falha aparente do servidor.

- **Limite diário de débito (teto do que pode sair da conta por dia)** — saque e transferência enviada dividem um mesmo teto diário por conta (`bank.limits.daily-debit`, padrão `10000.00`); estourá-lo volta **422** com o quanto ainda há disponível hoje, para o cliente reenviar um valor que passa em vez de tentar às cegas. É o controle que todo banco tem e existe para **limitar o estrago de uma conta comprometida** (senha vazada, celular roubado): sem teto, uma conta é esvaziada de uma vez só. Três decisões: **(1) o limite cobre toda saída de dinheiro, não só o saque** — se valesse apenas para `withdraw`, esvaziar a conta seria só usar `transfer`; a transferência consome o limite da conta **origem** e só dela, porque quem recebe não está tirando dinheiro da própria conta. A classificação débito/crédito vem de `TransactionType.debitTypes()`, derivada do `isCredit()` que o resumo do extrato já usava — um tipo novo no enum entra do lado certo sozinho, sem lista paralela para esquecer de atualizar. **(2) O "quanto já saiu hoje" é somado no banco** (`sumAmountByTypeSince`), como o resumo do extrato: o limite nunca carrega os lançamentos do dia para totalizar em memória, e o dia é o dia **UTC** — o mesmo referencial dos filtros de período do extrato —, então a janela não muda conforme o fuso do servidor. **(3) A checagem vem depois do débito no domínio**, de propósito: conta bloqueada/encerrada e saldo insuficiente mantêm a precedência na mensagem (quem está com a conta congelada precisa ouvir *isso*, não "limite excedido"), e nada é persistido quando o limite estoura porque a `BusinessException` faz rollback da transação. O ponto mais interessante é a **concorrência**: ler o total do dia e depois gravar é um *check-then-act*, e duas operações simultâneas na mesma conta poderiam ambas passar — quem fecha a janela é o **travamento otimista que já existia**: as duas alteram o saldo da mesma conta, então a segunda esbarra na `@Version`, recebe **409** e, ao ser repetida, refaz a checagem com o total atualizado. A decisão em si (*"cabe no que sobrou?"*) mora num value object (`DailyDebitLimit`), aritmética pura testável sem banco; buscar o total é do service, que tem o repositório. Sem migração: o limite é derivado dos lançamentos que já existem, não uma coluna nova.

- **Token que não identifica ninguém é 401, não 500** — o `JwtAuthenticationFilter` roda **antes** do `ExceptionTranslationFilter` do Spring Security (ele é registrado antes do `UsernamePasswordAuthenticationFilter`, e o tradutor vem depois na cadeia). Isso tem uma consequência que passa despercebida: exceção que escapa desse filtro **não vira 401** — ela escapa da cadeia de segurança inteira, não passa nem pelo `@RestControllerAdvice`, e cai no tratamento de erro do container como **500** com um corpo fora do `ApiError` padrão. O filtro só tratava `JwtException`, então dois casos reais escapavam. **(1) Token nosso, assinado e dentro da validade, cujo usuário não existe mais** (removido enquanto o token ainda valia): o `UserDetailsService` lança `UsernameNotFoundException` — que é uma `AuthenticationException`, mas nesse ponto da cadeia ninguém a traduz. Um token não deixa de ser apresentável só porque o usuário sumiu, então isso acontece em produção, e a resposta certa é claramente 401: a credencial não identifica mais ninguém. **(2) `Authorization: Bearer` sem token**: o parser recusa a string vazia com `IllegalArgumentException`, que não é `JwtException`. Nos dois casos o cliente recebia "erro interno do servidor" por uma credencial ruim — diagnóstico errado, e um 500 espúrio polui o sinal de saúde da aplicação (alarme e métrica de erro 5xx acusando falha nossa onde o servidor está funcionando exatamente como deveria). Agora a string vazia é barrada antes do parser e a `UsernameNotFoundException` entra no mesmo `catch`, ambos seguindo sem autenticar → **401** no corpo padrão. O ponto de design é o que **não** foi feito: o `catch` continua restrito a esses dois tipos em vez de engolir qualquer exceção. Uma falha de infraestrutura (banco fora do ar ao carregar o usuário) precisa continuar subindo e sendo 500 — transformá-la em 401 diria "seu token não presta" para um problema nosso, mandando o cliente trocar uma credencial que estava correta enquanto a falha real fica invisível. É o mesmo princípio dos itens acima, invertido: rede genérica não deve responder por causa que ela não conhece, e tratador específico não deve capturar mais do que sabe tratar.

- **Senha maior do que o bcrypt considera é recusada, não truncada em silêncio** — o `BCryptPasswordEncoder` só leva em conta os **72 primeiros bytes** da senha e **descarta o resto sem erro nem aviso** (é limite do algoritmo, não configuração). O cadastro aceitava `@Size(min = 8, max = 100)`, então uma senha de 100 caracteres era aceita e **guardada como o hash de um pedaço dela**. O modo de falha é o pior tipo: silencioso e do lado errado da segurança. A senha que o usuário acredita ter não é a que protege a conta — quem descobrir apenas o começo dela entra; duas senhas que compartilham os 72 primeiros bytes são **a mesma credencial**, então "trocar a senha" mexendo só no final não troca nada e a antiga continua funcionando; e uma frase-senha longa, justamente a prática que se recomenda ao usuário, é a que mais perde entropia. O ponto técnico é **em que unidade o limite é contado**: um `@Size(max = 72)` pareceria resolver e não resolveria, porque o bcrypt conta **bytes UTF-8**, não caracteres — 36 caracteres acentuados (2 bytes cada) ou 18 emojis (4 bytes cada) já preenchem o limite, e a senha seria truncada com metade dos caracteres permitidos. Daí uma constraint própria (`@BcryptPassword`, mesmo padrão do `@Cpf`) que mede a senha em bytes; o teto vive na constante `BcryptPassword.MAX_BYTES`, ligada ao algoritmo e não repetida solta. A checagem fica na **borda** (DTO) e volta **400** no corpo de erro padrão, antes de qualquer hash. Também é uma decisão o que **não** foi feito: as saídas usuais seriam pré-hashear a senha (SHA-256 antes do bcrypt) ou trocar para Argon2/scrypt, que não têm esse teto — as duas mudam o formato do hash guardado e exigiriam migrar as senhas existentes, então ficam para quando houver motivo maior. E o `login` **não** ganhou o limite de propósito: senha errada ali é **401**, não 400 (o endpoint de login não descreve a política de senha para quem está tentando adivinhar), e quem já tinha cadastro com senha longa continua entrando com ela — a mudança é retrocompatível.

- **Chave de idempotência tem prazo de validade (retenção + expurgo periódico)** — a tabela `idempotency_keys` ganhava uma linha (com o corpo da resposta junto) a cada operação com dinheiro e **nunca perdia nenhuma**. Crescimento sem fim já é ruim por si só, mas o detalhe que importa é *qual* tabela cresce: essa é lida e escrita no **caminho quente** de todo depósito, saque e transferência com `Idempotency-Key` — quanto maior o índice, mais caro fica exatamente a operação mais sensível da API; e o backup passa a carregar para sempre dados que ninguém vai consultar. Ninguém vai consultar porque a tabela é um **cache de respostas, não um livro-razão**: quem guarda o que aconteceu com o dinheiro é o extrato (`transactions`), esse sim permanente. Uma chave só serve enquanto o cliente ainda pode repetir a requisição — *retry* de timeout acontece em segundos ou minutos, não em dias. Daí uma **janela de retenção** (`bank.idempotency.retention`, padrão **24h**, o mesmo prazo que o mercado usa) e um expurgo periódico (`bank.idempotency.purge-interval`, padrão 1h) que apaga o que venceu. O ponto de design é a **assimetria dos dois erros possíveis**: apagar tarde demais só custa espaço, mas apagar **cedo demais** faz um *retry* legítimo reexecutar a operação — a chave que impediria o depósito em duplicidade não existe mais. Por isso a janela é generosa e configurável, e a regra é que ela seja sempre maior que a janela de *retry* do cliente. Dois detalhes de implementação: o expurgo é um `delete` **em massa no banco** (`delete ... where created_at < :cutoff`), e não o `deleteByCreatedAtBefore` derivado — que o Spring Data implementa carregando cada linha como entidade para remover uma a uma, ou seja, um dia inteiro de operações em memória; e a migração `V6` cria um índice em `created_at`, senão o expurgo vira um *scan* na tabela inteira a cada execução. O trabalho é **best-effort de propósito**: uma chave vencida sobreviver até a próxima rodada não quebra nada, e várias instâncias rodando o expurgo ao mesmo tempo também não (o `delete` é idempotente e todas removem só o que já venceu) — um lock distribuído (ShedLock) seria para não repetir trabalho, não para evitar corrupção.

- **Crédito que não cabe na coluna é recusado como regra de negócio, não estourado no banco** — o saldo mora numa coluna `NUMERIC(19,2)`, então existe um valor máximo que a conta consegue guardar: `99999999999999999.99`. A validação de entrada já limitava **cada valor** ao que cabe (`@Digits(integer = 17, fraction = 2)`), mas ninguém olhava o **acumulado**: dois depósitos individualmente válidos somavam um saldo grande demais para a coluna. O erro só aparecia no *flush*, como `DataIntegrityViolationException`, e caía na rede de segurança genérica do handler — que **não sabe qual restrição falhou** e responde **409 "conflito de concorrência na gravação, requisição já em processamento"**. É o pior tipo de resposta errada: aponta uma causa que não existe (não houve concorrência nenhuma) e ainda **convida ao retry**, e o retry vai falhar exatamente igual, para sempre. É o mesmo modo de falha dos itens do CPF e do username acima, aqui vindo do estouro de capacidade em vez de uma coluna única. Agora quem conhece a causa recusa antes: o **domínio** é o único que sabe o saldo atual, então `Account.deposit` checa se o saldo resultante cabe e levanta a mesma `BusinessException` de "saldo insuficiente" — **422**, com quanto ainda cabe na conta, para o cliente reenviar um valor que passa. Fica simétrico e fácil de explicar: o saque tem um **piso** (zero, sem cheque especial) e o depósito tem um **teto** (a capacidade da coluna). A regra vale para **todo crédito**, não só o depósito: uma transferência para uma conta cheia falha **atomicamente** pela mesma checagem (`Account.deposit` é a porta única de entrada de dinheiro), então ninguém é debitado. O teto não é um número solto no código: é `Money.MAX`, **derivado** de `Money.PRECISION`/`Money.SCALE` — as mesmas constantes que agora preenchem os `@Column(precision = ..., scale = ...)` das entidades (o mesmo truque do `IdempotencyRecord.KEY_MAX_LENGTH`). Coluna e regra saem da mesma fonte, então não dá para aumentar a capacidade do banco e esquecer a regra, nem o contrário.

- **CPF do titular sai mascarado da API (minimização de dado pessoal)** — o `document` entrava inteiro na criação da conta e **voltava inteiro em toda resposta**: criação, consulta, depósito, saque, as duas contas de uma transferência e — o pior caso — a **listagem paginada**, onde uma única chamada devolvia o CPF completo de *todos* os titulares, até 100 por página. O CPF precisa ser guardado inteiro (é a chave de negócio do titular e a coluna `UNIQUE` que garante uma conta por pessoa), mas **não precisa sair inteiro**: quem já tem a conta não aprende nada lendo o próprio documento de volta, e o identificador que o cliente usa para operar é o `id` (UUID) — nenhuma rota recebe CPF, então mascarar a saída **não quebra nenhum fluxo**. O que muda é o alcance do dado: todo CPF que sai da API vira cópia fora do nosso controle (cache do cliente, log de proxy, corpo de resposta guardado sob uma `Idempotency-Key`), e um vazamento em qualquer um desses pontos não é mais nosso para conter. O formato segue a convenção brasileira de exibição parcial, `***.456.789-**` — escondidos os três primeiros dígitos e os dois verificadores —, o bastante para o titular reconhecer o próprio documento. E vale ser honesto sobre o que isso **não** é: não é sigilo criptográfico (os verificadores são deriváveis dos nove primeiros dígitos), é **minimização** — a API para de espalhar por atacado um identificador completo que ninguém precisa para operar. Duas decisões de implementação: **(1)** a máscara é aplicada em `AccountResponse.from`, o **único ponto** onde uma `Account` vira resposta — mesma escolha do `Money.normalize`, para que nenhum endpoint (nem um endpoint futuro) possa esquecer de aplicá-la; foi assim que a transferência, que devolve as duas contas, saiu protegida sem o service precisar saber disso. **(2)** Entrada fora do formato esperado vira máscara **total** (`***.***.***-**`), não o valor cru: uma função de mascaramento que devolve o original quando não reconhece a entrada não protege justamente o caso que ela existe para cobrir — *fail closed*.

- **Transferência trava as contas sempre na mesma ordem (evita *deadlock*)** — uma transferência atualiza **duas** linhas de `accounts` na mesma transação, e cada `UPDATE` segura um *lock* naquela linha até o commit. Carregando origem-e-depois-destino, a ordem dos *locks* passa a depender do **sentido** da transferência — e duas transferências simultâneas em sentidos opostos entre as **mesmas** contas travam uma na outra: `A→B` pega a linha de A e pede a de B enquanto `B→A` pega a de B e pede a de A; ninguém solta o que já tem, e o banco quebra o impasse **matando uma das duas**. Não é um cenário exótico: duas pessoas se pagando ao mesmo tempo, ou qualquer par de contas com tráfego nos dois sentidos, já basta. Agora as duas contas são carregadas em **ordem canônica** (a de menor UUID primeiro, qualquer que seja a origem), então as duas transações pedem os mesmos *locks* na mesma sequência e a segunda apenas **espera** a primeira terminar — o ciclo não chega a se formar. Três pontos que valem a explicação: **(1) o travamento otimista já existente não cobria isso** — a `@Version` evita *lost update* (uma gravação sobrescrever a outra), não a espera circular por *locks* de linha, que acontece antes, dentro do banco; são problemas diferentes com soluções diferentes. **(2) Quem define a ordem dos `UPDATE`s é a ordem de *carga*, não a das chamadas a `save`**: as contas já estão gerenciadas pela transação, então o `save` não emite SQL na hora — o Hibernate emite os `UPDATE`s no *flush*, seguindo a ordem em que as entidades entraram no contexto de persistência. Ordenar os `save` seria cosmético; a ordem é imposta no `loadPair`. **(3) O que acontecia com a vítima**: o *deadlock* sobe como `CannotAcquireLockException`, que **não** é a `OptimisticLockingFailureException` já tratada — caía na rede de segurança final e virava **500**, a API se declarando defeituosa por uma disputa de concorrência normal e ainda escondendo do cliente que valia a pena repetir. O caminho conhecido foi fechado na origem pela ordenação, e um *handler* de `PessimisticLockingFailureException` ficou como rede de segurança, devolvendo **409** (mesmo status da falha otimista: a operação não aconteceu e repetir tende a funcionar). Um *deadlock* de verdade não é reproduzível de forma determinística num teste, então o que os testes fixam é a **invariante** que o evita: a ordem de carga não muda com o sentido da transferência.

- **Paginação da listagem ordena por uma ordem *total* (desempate por id)** — a listagem de contas ordenava só por `createdAt desc`, e `createdAt` **não é único**: duas contas criadas no mesmo instante empatam (concorrência sob carga, ou uma carga em lote vinda de um sistema legado, em que a coluna inteira recebe o mesmo valor). Para linhas empatadas o banco não promete ordem nenhuma — pode devolvê-las numa ordem diferente a cada execução, conforme plano, paralelismo ou até em qual página do disco a linha está. Isso só é inofensivo enquanto a lista é lida de uma vez; a paginação por **`offset`** recorta a lista **por posição**, e cada página é uma consulta nova: se a ordem mudar entre a página 1 e a página 2, uma conta **aparece nas duas** e outra **não aparece em nenhuma**. O modo de falha é o pior tipo — não há erro, não há status diferente, apenas um registro que some da listagem e um cliente varrendo páginas para conciliar que nunca vê a conta. A correção é uma coluna a mais no `ORDER BY`: com `a.id desc` no desempate **não existem linhas empatadas**, a ordenação vira uma ordem total, a ordem é a mesma em toda execução e o recorte por página fica estável. O ponto que vale a explicação é que **a query do extrato já fazia isso certo** (`order by t.createdAt desc, t.id desc`) — é a mesma lição transversal dos itens do CPF e do username acima: quando duas rotas dependem do mesmo cuidado, acertar uma e esquecer a outra deixa o comportamento inconsistente entre endpoints. Um reordenamento de empate não é reproduzível de forma determinística num teste (depende do banco), então os testes fixam a **invariante que o evita**: contas com o mesmo `createdAt` voltam ordenadas por id decrescente, e percorrer as páginas devolve cada uma exatamente uma vez. Detalhe do teste que virou decisão: os ids são **escolhidos**, não gerados, porque Java compara `UUID` como dois `long` **com sinal** e o banco os compara como 16 bytes **sem sinal** — para UUIDs aleatórios as duas ordens divergem, e o teste estaria afirmando a ordem errada. Sem migração: é só a cláusula de ordenação da consulta.

- **O índice do extrato acompanha a consulta que existe, não só o filtro por conta** — a tabela `transactions` tinha um índice por `account_id`, criado junto com o schema, quando o extrato ainda era "todos os lançamentos da conta". Desde então a consulta mudou três vezes (paginação, filtro por período, filtro por tipo) e o índice não: hoje **nenhuma** das três consultas da tabela é só uma igualdade. O extrato pede *uma conta, do mais recente para o mais antigo, uma página* (`where account_id = ? order by created_at desc, id desc` + `limit`); o resumo e a soma do limite diário pedem *uma conta, dentro de uma janela de tempo* (`created_at >= ?`). Um índice só por `account_id` atende a parte do `where` e para aí — o banco lê **todos** os lançamentos da conta e os ordena para devolver 20. O efeito é o custo crescer com o tamanho da **conta** em vez de com o tamanho da **página**: numa conta com muito histórico a página 1 custa o mesmo que a página 500, e é justamente a conta movimentada (a que mais consulta o extrato) que fica mais cara. Com `(account_id, created_at, id)` o banco posiciona no início da conta e caminha pelo índice **já na ordem pedida**, parando no `limit`; o recorte por período vira um trecho contíguo do índice em vez de um filtro linha a linha. A ordem das colunas é a decisão inteira — invertida, o índice viraria enfeite —, e o `id` entra como terceira coluna pelo mesmo motivo que entra no `order by`: é o desempate que torna a ordenação total (ver o item de paginação estável acima). O índice antigo é **removido** na mesma migração: `account_id` é o prefixo à esquerda do novo, então tudo que o usava continua atendido e manter os dois só custaria escrita a cada lançamento — o `DROP` vem depois do `CREATE` para a tabela nunca ficar sem índice por conta (a FK para `accounts` também se apoia nele). Dois detalhes que viraram decisão: o índice é declarado **também na entidade** (`@Table(indexes = ...)`), não só na migração Flyway, senão ele existiria apenas no Postgres e o H2 de dev/teste — onde o Hibernate cria o schema — rodaria sem ele; e o teste afirma a **ordem das colunas**, não a existência do índice, porque o custo real de um plano de execução não é afirmável de forma determinística num teste — o que dá para prender é a estrutura que o torna possível. Migração `V7__replace_transactions_account_index.sql`.

- **`Idempotency-Key` vive no escopo do cliente, não num namespace global** — a chave era a `PRIMARY KEY` da tabela sozinha, ou seja, **um único namespace para todos os clientes da API**. Mas a `Idempotency-Key` é uma string **escolhida pelo cliente**: ela é o nome que *aquele* cliente deu a uma requisição *dele*, não um identificador global. Dois clientes escolherem a mesma string não é hipótese remota — `1`, `retry-1`, `pagamento-do-mes` são chaves que qualquer um digita, e a API aceita qualquer texto de até 255 caracteres —, e quando isso acontecia a chave de um passava a **decidir o destino da requisição do outro**, com dois desfechos, os dois ruins. **(1)** Se as requisições eram diferentes, a impressão digital (item acima) não batia e o segundo cliente levava **409 "chave já utilizada para uma requisição diferente"** — sobre uma chave que ele estava usando pela primeira vez. É um erro que ele não consegue diagnosticar (nada do lado dele está errado) nem contornar sem adivinhar que precisa trocar de chave. **(2)** Pior: se as requisições **coincidiam** (mesma operação, mesma conta, mesmo valor — plausível, já que qualquer cliente autenticado pode operar qualquer conta), a impressão digital batia e o segundo cliente recebia **200 com a resposta guardada do primeiro**. A operação dele nunca acontecia, e nada na resposta indicava isso: o depósito "confirmado" que não creditou — exatamente o modo de falha que a impressão digital foi criada para eliminar, sobrevivendo por um motivo que ela não cobre. É a lição do item anterior levada um nível acima: a impressão digital responde *"é a mesma requisição?"*, e faltava responder *"é o mesmo cliente?"*. Agora a identidade do registro é o **par (cliente, chave)** — chave primária composta —, então a mesma string vinda de clientes diferentes são registros diferentes, e a chave só pode devolver a resposta de uma requisição do próprio dono. O escopo é o **subject do JWT** (o username autenticado), guardado como **hash SHA-256**: a tabela só precisa responder "foi o mesmo cliente?", nunca dizer quem ele é — mesma justificativa (e mesmo formato de coluna) da impressão digital da requisição, com o bônus de a coluna ter largura fixa e não depender do tamanho do username. O que **não** mudou: a colisão de duas requisições concorrentes com a mesma chave continua sendo barrada pela chave primária (agora composta) e voltando **409**, e o *retry* legítimo do próprio cliente continua memoizado. Detalhe da migração `V8`: trocar a coluna da chave primária exige **recriar a tabela** (não há DDL portável entre PostgreSQL e H2 para dropar uma PK que o banco nomeou), o que aqui é barato **de propósito** — essa tabela é um *cache* de respostas com 24h de retenção, não o livro-razão; as linhas existentes são preservadas sob o escopo sentinela `-` e saem sozinhas no próximo expurgo. Como *deadlock* e reordenamento de páginas, o cenário não é reproduzível de forma determinística num teste de concorrência — então os testes fixam a **invariante**: a mesma chave, vinda de dois clientes, produz dois efeitos independentes (saldo 300, não 150).

- **Consulta dos limites da conta (`GET /accounts/{id}/limits`) — o mesmo cálculo do enforcement, nunca um paralelo** — o limite diário de débito existia só como recusa: o cliente descobria quanto podia movimentar **estourando o teto** (422) e lendo o disponível na mensagem de erro — usar um erro como consulta. Agora há um endpoint de leitura que devolve o teto configurado, o quanto já saiu da conta na janela de hoje (dia UTC) e o quanto ainda há disponível — o que todo app de banco mostra antes de o usuário digitar o valor. A decisão central é **não existir um segundo cálculo**: a consulta usa a mesma soma no banco (`sumAmountByTypeSince`, saques + transferências enviadas desde a meia-noite UTC) e a mesma aritmética (`DailyDebitLimit.remaining`, extraída do `ensureAllows`) que barram as operações — o número que a consulta informa é, por construção, o número que a próxima operação vai obedecer; um teste fixa exatamente isso (o `availableToday` informado passa, um centavo a mais estoura citando o mesmo valor). O disponível **nunca é negativo**: se o teto configurado baixou depois de o dinheiro já ter saído, volta `0.00`, não um número que o cliente não sabe interpretar. A resposta é um envelope (`{ "dailyDebit": { ... } }`) de propósito — um limite futuro (ex.: teto por transação) entra como campo irmão sem quebrar o contrato. E vale dizer o que a consulta **não** é: uma **foto, não uma reserva** — entre consultar e operar, outra operação pode consumir o limite; quem decide de verdade é sempre a checagem dentro da operação (protegida pelo travamento otimista, ver o item do limite acima). Conta congelada continua enxergando os próprios limites (consultar é leitura, como o extrato); conta inexistente volta **404**. Sem migração: é uma leitura sobre os lançamentos que já existem.

- **A métrica de negócio conta a operação depois do commit, não durante a transação** — o counter `bank.account.operations` sempre se descreveu como "operações **concluídas**", mas era incrementado **dentro** da transação, na última linha do método do service. Só que uma operação com dinheiro não está concluída ali: ela está concluída quando **commita**. E o passo mais provável de falhar é justamente o último — `repository.save()` numa entidade já gerenciada **não emite SQL na hora**; o Hibernate manda os `UPDATE`s no *flush*, e é ali que roda a checagem do travamento otimista (`WHERE version = ?`). Ou seja: a operação passa por todas as regras do domínio, chega ao fim do método, incrementa o contador — e ainda pode não acontecer, virando **409** para o cliente. São pelo menos três caminhos que abortam depois da contagem: a falha otimista no *flush*, a colisão da mesma `Idempotency-Key` enviada em paralelo (a chave é gravada logo após a operação, e a violação da PK sobe no commit) e qualquer falha de infraestrutura no commit. O ponto que faz isso valer a correção é **onde** o erro se concentra: a contagem infla exatamente sob **contenção** — quando duas operações disputam a mesma conta e uma é rejeitada —, que é precisamente quando alguém está olhando o painel para entender o que está acontecendo. E o sintoma é silencioso: nenhum erro, nenhum status diferente, só um total de depósitos que **nunca fecha com o extrato** — e o extrato, gravado na mesma transação, é quem está certo; a métrica é que conta tentativas se dizendo conclusões. A correção é adiar a contagem para depois do commit com um `TransactionSynchronization` (`afterCommit`): se a transação faz rollback, o *hook* simplesmente nunca roda. O *hook* é **síncrono e na mesma thread**, executado antes de o método transacional devolver o controle, então a métrica já está atualizada quando a resposta HTTP é escrita — não há janela em que o cliente vê o sucesso e o painel ainda não. O erro fica **assimétrico e do lado seguro**: uma operação committada é sempre contada e uma abortada nunca é, e não existe o inverso (contar a mais) porque nada depois do commit desfaz a operação. Duas decisões menores: os contadores saíram do `AccountService` para um `OperationMetrics` próprio — o serviço volta a só chamar "conte esta operação", sem saber o que é sincronização de transação —, e os três counters continuam **registrados no start da aplicação**, não na primeira operação, senão o painel começaria com uma série ausente em vez de um zero. Sem transação ativa (uso direto do serviço em teste ou tarefa interna) a contagem é imediata: não há commit para esperar, e um contador que se recusasse a contar seria pior que um aproximado.

- **O esquema de autenticação faz parte do contrato OpenAPI (bearer JWT declarado, não só imposto)** — as rotas de conta exigem `Authorization: Bearer <token>` desde a autenticação JWT, mas o documento OpenAPI **não dizia isso**: o `SecurityConfig` impunha a regra em runtime e o contrato publicado seguia descrevendo uma API aberta. O efeito mais visível era o Swagger UI **sem o botão Authorize** — todo "Try it out" numa rota protegida voltava 401 sem existir onde colar o token, ou seja, a própria documentação interativa não conseguia exercitar a API que documenta; o efeito mais sério é que o documento é o contrato **legível por máquina**: um cliente gerado a partir dele (openapi-generator) nasceria sem saber que precisa enviar o cabeçalho, e a diferença entre "o servidor recusa" e "o contrato declara" é exatamente a diferença entre descobrir isso em produção ou no code-gen. A declaração espelha a estrutura do `SecurityConfig`: o requisito é **global** (`security` no topo do documento) porque proteger é a regra — uma rota nova nasce documentada como protegida sem ninguém lembrar de anotá-la, o mesmo raciocínio do `anyRequest().authenticated()` —, e as poucas rotas públicas se **isentam localmente** com `@SecurityRequirements` vazio (que vira `security: []` na operação): cadastro/login, onde o token é obtido — exigir token ali seria circular — e o health de probe. Os testes afirmam o **contrato, não a configuração**: leem o `/v3/api-docs` servido e conferem o esquema (`http`/`bearer`/`JWT`), o requisito global, a herança nas operações protegidas (que não devem repetir o requisito localmente) e o `security: []` nas públicas — com `hasSize(0)` de propósito, porque o `isEmpty()` do MockMvc também passa quando o campo nem existe, que aqui seria justamente o bug.

- **Troca de senha exige a senha atual, e senha atual errada é 422 — não 401** — cadastro e login existiam desde o dia do JWT, mas um usuário com senha vazada não tinha como **rotacioná-la** sem alguém mexer no banco: a credencial que protege tudo era a única coisa da API que não podia ser trocada. Agora `PUT /api/v1/users/me/password` troca a senha do dono do token; três decisões. **(1) A senha atual é obrigatória mesmo com o token já provando quem é o usuário** — é uma *reautenticação*: um token roubado (ou uma sessão deixada aberta) não pode virar uma troca de senha que tranca o dono de verdade para fora. **(2) Senha atual errada volta 422, não 401.** O 401 tem um significado para o cliente — *"seu token não vale, vá para o login"* — e aqui o token vale perfeitamente; o que está errado é um campo do corpo. Devolver 401 faria um cliente bem-comportado descartar um token válido e derrubar o usuário para o login por causa de um erro de digitação. Pela mesma razão a conferência é feita com o `PasswordEncoder.matches` contra o hash guardado, não com o `AuthenticationManager` (que é o caminho do login e lança `AuthenticationException` → 401). Nova senha igual à atual também é 422: "trocar" para a mesma senha não invalida nada, e quem troca por vazamento precisa que a antiga deixe de valer. **(3) A rota fica fora de `/api/v1/auth/**` de propósito** — aquele prefixo está liberado inteiro no `SecurityConfig` (é onde se obtém o token; exigir token ali seria circular). Colocar uma rota protegida lá dentro dependeria de uma exceção listada *antes* do `permitAll` — regra que funciona hoje e quebra em silêncio na próxima edição da lista. Em `/api/v1/users/me/**` a rota cai no `anyRequest().authenticated()` sem exceção nenhuma, e o `/me` deixa explícito que o alvo é sempre o dono do token, nunca um id vindo da URL. A nova senha reusa **as mesmas anotações** do cadastro (`min 8` e o teto em bytes do bcrypt, `@BcryptPassword`), então a troca não tem como aceitar uma senha que o cadastro recusa. O que fica registrado como limitação conhecida: com JWT *stateless*, os tokens já emitidos **continuam válidos até expirarem** (60 min por padrão) — a troca invalida a senha antiga para novos logins, não as sessões em curso; invalidar tokens anteriores à troca pediria estado no servidor (ou um `passwordChangedAt` conferido a cada requisição), decisão separada. Os testes rodam o fluxo inteiro com token de verdade (cadastro → troca → login): a nova senha entra, a antiga não; senha atual errada não muda nada; a troca de um usuário não encosta na senha de outro.

- **Perfil do usuário autenticado (`GET /users/me`) com contrato fechado** — o cliente precisa saber *quem o token representa* (o clássico `/me` que todo app chama logo após o login para montar a tela), e até aqui a API só devolvia o token cru no cadastro/login. O username vem do **subject do token**, nunca da URL — não existe "perfil de outro usuário" nesta API, e a rota fica em `/users/me/**` pelo mesmo motivo da troca de senha (cai no `anyRequest().authenticated()` sem exceção). A resposta é um **record separado da entidade** (`UserProfileResponse`: `id`, `username`, `createdAt`): `AppUser` carrega o `passwordHash`, e a única forma de garantir que ele **nunca** sai pela API é não existir campo para ele no DTO — não depende de `@JsonIgnore` nem de alguém lembrar de não serializar a entidade. O teste fecha o contrato (`$.*` com exatamente 3 campos e o corpo sem o hash nem a senha), então um campo novo na entidade não vaza sem passar por ele. Leitura pura, `@Transactional(readOnly = true)`.
